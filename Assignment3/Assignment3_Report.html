4. Q3 — Resource safety, debugging and robust code

Manual finally { close(); } is fragile if an exception occurs before every resource is registered for closure, if one close throws before later closes run, or if control paths omit a close. A deliberately failing second-store input should be used while stepping through open/read/close operations. Log the store path and failure type; count open descriptors before and after each version using a debugger/OS diagnostic. Those measurements have not been performed.

try (BufferedReader in = Files.newBufferedReader(input);
     BufferedWriter out = Files.newBufferedWriter(summary)) {
    // read, validate and aggregate one store at a time
} catch (IOException e) {
    // log store identity and report failure
}

Try-with-resources closes resources in reverse declaration order, even after exceptions. If the body throws and close also throws, the body exception remains primary and the close failure is available through getSuppressed(). It is not sufficient by itself if output must be atomic, partial results must be rolled back, errors must be retried, or inputs are semantically corrupt. For f files and total input size N, processing is O(N) time. Sequential try-with-resources uses O(1) open-file handles; opening all files first can use O(f) handles. Manual closing/no closing can leak up to O(f) handles in a failure path.

5. Q4 — Thread creation and lifecycle

NEW → RUNNABLE ↔ (BLOCKED / WAITING / TIMED_WAITING) → TERMINATED

A station can extend Thread or implement Runnable. Runnable separates work from the thread object and still allows extending another class, so it is generally more reusable. Call start() to schedule a new thread; calling run() is an ordinary synchronous method call. sleep() pauses the current thread without releasing held monitors; join() makes the caller wait for completion; isAlive() reports whether a thread has started and not terminated.

for (Thread station : stations) station.start();
for (Thread station : stations) station.join();
// only now compute/print the final aggregate

Completion order is scheduler- and workload-dependent; record at least ten real runs. Thread priority is only a scheduling hint, not an ordering guarantee. A daemon can be stopped when the last user thread ends, so it must not own essential final output. No run-order or priority data is reported as measured. With n scripts and p workers, idealized work time may approach O(n/p) for balanced independent batches, but I/O and coordination add overhead. An ExecutorService bounds the number of thread stacks to p rather than creating one thread per station/task.

6. Q5 — Cinema seat-booking race

The critical operation is the check-then-set plus increment. Without atomicity, two threads can both observe booked[s] == false, both set it, and both increment the count. One valid interleaving is: A checks false → B checks false → A marks/increments → B marks/increments. The supplied program expects ten seats sold for 100 attempts across ten seats; the synchronized source uses a synchronized instance method, which locks the shared SeatBooking instance.

public synchronized void book(int seat) {
    if (!booked[seat]) {
        booked[seat] = true;
        bookingsMade++;
    }
}

A synchronized block on the same instance around only this critical section has equivalent correctness and may reduce lock scope if other method work is independent. A static synchronized method locks the Class object and is needed only if state is shared across all instances; otherwise a per-screen lock provides better independence. The method/block each use an intrinsic monitor. Compare 10,000 attempts and ten repeated unsynchronized runs as specified; no timing or race-count result is available. For s seats, boolean-array synchronization is O(1) per booking and O(s) state. AtomicBoolean per seat / a map with putIfAbsent / ReentrantLock can provide atomic reservation, but add object or map overhead; contention can increase latency. For 20 screens, use independent screen-level state and synchronization per screen, with a durable database uniqueness constraint for multi-process booking.

7. Q6 — Deadlock and inter-thread communication

Two transfers can deadlock if thread A holds wallet A and waits for B while thread B holds B and waits for A. This exhibits mutual exclusion, hold-and-wait, no preemption and circular wait. Assign every account a stable ordering key and always lock the lower key first; the rule removes circular wait. If locks are acquired with a timeout, retry or fail the transfer without applying a partial debit.

For a capacity-five token counter, guard state with the same monitor and use while, not if, because a wake-up does not guarantee the condition remains true (and spurious wakeups are permitted):

put(token): synchronized
  while count = 5: wait()
  buffer[in] ← token; in ← (in + 1) mod 5; count ← count + 1
  notifyAll()
take(): synchronized
  while count = 0: wait()
  token ← buffer[out]; out ← (out + 1) mod 5; count ← count - 1
  notifyAll(); return token

wait() releases the monitor and suspends until notified; sleep() does not release a monitor. notifyAll() lets all waiters re-check their predicates; notify() may wake a waiter whose condition is still false and leave a suitable waiter asleep. The expected sum for tokens 1–20 is 210 and the buffer invariant is 0 ≤ count ≤ 5. The supplied Task06 implementation follows the expected algorithm, but execution is unverified. ArrayBlockingQueue<Integer>(5) encapsulates bounded blocking and is less error-prone. Put/take are O(1) amortized, storage O(5); ordered locking transfers are O(1) lock operations, with contention-dependent waiting.

8. Q7 — Concurrent fault-tolerant result processor

Measurable requirements: process each input exactly once; a missing/corrupt file is recorded as a failure without stopping other files; success + failure count equals submitted count; every result/failure has an input identifier; all workers finish before the summary is emitted. Shared mutable results require a thread-safe collection.

ResultProcessor → ExecutorService(p)
  submits Callable<ProcessingResult> for each score file
  Future.get() records success or ExecutionException failure
  concurrent result/failure collections → final immutable summary

Use a fixed pool and bounded submission strategy for 10,000 files to avoid holding unnecessary queued tasks. Each Callable opens its own input, validates it, computes one result and returns a value; catch expected per-file failures at the task boundary and include their paths. On cancellation/interruption, restore the interrupt flag and shut down the executor in a finally-safe lifecycle.

for each file: submit Callable(read → validate → compute)
for each Future: get; add result, or record that task's failure
assert successes + failures = input count
shutdown; await termination; report totals and per-file failures

Measure wall-clock time for p ∈ {1, 2, 4, 8}, repeat runs, use the same fixed input set, and retain raw times, JVM/OS details and counts. No 10,000-file dataset or actual timing was run, so no fabricated speedup or recommended pool size is asserted. Parallel streams use a shared common pool and are concise but offer less explicit resource control. One thread per file uses O(n) thread stacks and can exhaust resources. ExecutorService caps thread stacks at O(p). One corrupt file is best handled per task rather than failing the entire parallel operation.
