2. Part A — Persistence design and pseudocode

A1 — File format design

Text record: one UTF-8 line containing passId, registerNumber, name, routeNumber, boardingStop, ISO validityDate and decimal amount. A robust delimited format must quote/escape delimiters, quotes and newlines; naive comma splitting is only safe if fields prohibit commas/newlines. A damaged record is rejected and logged by line number while scanning continues. Missing file is distinguished from an empty file. To reduce power-loss damage, write a complete replacement to a temporary file, flush/close it, then atomically move it over the original where supported; append-only records can additionally use checksums/recovery markers.

Binary layout with DataOutputStream: file header (magic, format version); record count or length-prefixed records; UTF-8 field lengths and bytes (or documented writeUTF constraints); date as epoch-day integer; amount as integer cents or a fixed decimal representation. Validate lengths and version before allocating/reading. A truncated final record is detected as EOF inside a record and reported, not silently treated as valid.

SIMATS-style pseudocode — structured and language-independent:

ALGORITHM AddPass
INPUT: pass record P, file path F
OUTPUT: success or validation/I-O failure
BEGIN
  VALIDATE required fields and amount of P
  OPEN F in append mode with buffered UTF-8 writer
  ENCODE P using documented escaping
  WRITE encoded record and line terminator
  FLUSH and CLOSE writer
  RETURN success
END
ALGORITHM FindPass
INPUT: pass identifier ID, file path F
OUTPUT: matching pass or NOT_FOUND
BEGIN
  IF F does not exist THEN RETURN NOT_FOUND
  OPEN F with buffered reader
  FOR each line L with line number
    PARSE L; IF malformed THEN record diagnostic; CONTINUE
    IF parsed pass identifier equals ID THEN CLOSE; RETURN pass
  END FOR
  CLOSE; RETURN NOT_FOUND
END
ALGORITHM ListRoute
INPUT: route number R, file path F
OUTPUT: all valid pass records for R
BEGIN
  OPEN F with buffered reader
  FOR each line L
    PARSE L; IF malformed THEN record diagnostic; CONTINUE
    IF parsed route equals R THEN EMIT parsed pass
  END FOR
  CLOSE
END

For n records, sequential add is O(1) amortized append (excluding storage/flush costs); find and list are O(n) time, O(1) scan memory. Fixed-length RandomAccessFile records enable direct offset lookup O(1) when the key maps to a known slot, but impose fixed field capacity and costly shifts/reorganization for variable-length data. A separate index is needed for arbitrary IDs.

A2 — Buffered I/O

A 50 MiB file is 52,428,800 bytes; a one-byte read loop makes that many Java read calls. Buffering in 8 KiB chunks needs about 6,400 buffer refills (ceil(52,428,800 / 8,192)); actual OS calls depend on the stream implementation and are not exactly equal to Java reads. Buffering amortizes call overhead. It helps little for already-buffered streams, very small in-memory files, or workloads dominated by computation/network latency.

ALGORITHM CountLinesBuffered
INPUT: file F
OUTPUT: number of text lines
BEGIN
  count ← 0
  OPEN F using buffered character reader
  WHILE next line exists
    count ← count + 1
  END WHILE
  CLOSE F; RETURN count
END

Streaming buffered count is O(n) time and O(buffer-size) auxiliary memory. Files.readAllLines() is O(n) time but O(n) memory for all strings/list overhead; it is convenient for small files, risky for 50 MiB or larger inputs. Correct line semantics must count a final unterminated line consistently. Benchmark cold/warm runs across multiple file sizes and report environment and repeated measurements; none were captured.

A3 — Generic DAO design

Common operations in StudentDB, CourseDB and MarksDB are connection acquisition, parameter binding, execution, mapping ResultSet rows to objects, resource closure and error translation. Table names, key fields, columns and row mapping differ.

INTERFACE Dao<T, K>
  insert(entity: T): result
  findById(id: K): optional T
  findAll(): list of T
  update(entity: T): result
  delete(id: K): result
END INTERFACE

StudentDao implements Dao<Student, Integer>. Example mapping: Student.id → student.student_id primary key; name → student.name; registerNumber → student.register_number; courseId → student.course_id. SQL stays in the DAO; service/GUI code depends on the interface. A generic DAO reduces duplicated mechanics but should not erase genuinely table-specific query intent. Direct SQL in services/GUI tightly couples persistence and behavior and makes testing/reuse harder.

A4 — Serialization design

Hostel serialization traverses its reachable serializable object graph, including rooms and residents. Every non-transient reachable object must support serialization, otherwise serialization fails. A live JDBC Connection must be transient because it represents a process/resource handle and is not portable. A password should not be serialized at all; if a legacy class still has it, mark it transient and use a credential vault/rehydration mechanism instead. A phone number is ordinary persisted data, but adding it changes the class schema: define an explicit serialVersionUID, provide compatible defaults/migration, and test old fixtures. Native Java serialization is Java-specific and can be unsafe for untrusted input; CSV/JSON are inspectable and interoperable but need explicit versioning, escaping and validation.

A5 — Transaction correctness and SQL safety

ALGORITHM Transfer
INPUT: source wallet S, destination wallet D, amount A
OUTPUT: committed transfer or failure without partial balance change
BEGIN
  VALIDATE A > 0 and S ≠ D
  OPEN connection; DISABLE auto-commit
  TRY
    UPDATE S balance = balance - A WHERE balance ≥ A
    IF affected rows ≠ 1 THEN RAISE transfer failure
    UPDATE D balance = balance + A
    IF affected rows ≠ 1 THEN RAISE transfer failure
    COMMIT
  CATCH any database/validation failure
    ROLLBACK; REPORT failure
  FINALLY restore auto-commit and CLOSE connection
END

Two independent auto-commit updates can debit successfully and fail before credit, losing value. A single transaction commits both or rolls both back. Concatenating user input into login SQL allows input to alter query structure; this is prevented with PreparedStatement placeholders, bound parameters, least-privilege accounts and generic failure messages. The assignment's unsafe and safe versions should be tested only against a disposable local database. No literal bypass input is reproduced here.

B4 — Migration and final engineering decision

ALGORITHM MigratePassFile
INPUT: source file F, JDBC connection C, batch size B
OUTPUT: inserted count and validation-failure report
BEGIN
  READ database/driver metadata; list tables
  BEGIN transaction
  FOR each input record
    PARSE and VALIDATE; IF invalid THEN log source line and CONTINUE
    BIND values to PreparedStatement; add to batch
    IF batch size reached THEN EXECUTE batch; update counts
  END FOR
  EXECUTE remaining batch; COMMIT
  ON database failure: ROLLBACK and report failure
  CLOSE all resources
END

At 12 campuses and 100× the current volume, a shared relational database is the preferred system of record for concurrent counters, cross-campus queries, constraints, transactions, backup and access control. A single text file is simple but scans linearly and has weak concurrency/update guarantees. Java serialization is language/runtime-coupled and unsuitable as a shared multiuser datastore. Separate per-campus serialized files offer isolation but complicate global search, schema migration, recovery and consistent reporting. Preserve raw files as import/archive data, validate them, then migrate in bounded batches; make imports idempotent and report rejected records.
