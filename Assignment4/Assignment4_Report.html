2. Task 1 — GUI design review: fee payment

Diagnosis

Design defectImpactRefinement

No validationEmpty, malformed or negative amounts reach processingValidate required fields and numeric range in service

No clear feedback or receipt flowUser cannot tell success/failure or obtain receiptDisplay status and enable receipt only on success

Resources/errors not managedLeaks connections and hides failure causestry-with-resources and user-safe error mapping

Class structure: FeePaymentFrame collects/displays data; FeeService validates amount, invokes payment operation and returns a result; FeeRepository owns database access; ReceiptView renders a confirmed result. Event handlers translate UI actions into service calls, not SQL.

Pay Action → validate form → SwingWorker.doInBackground()
          → FeeService.pay(request) → FeeRepository (JDBC)
          → done(): show status / enable receipt on EDT

Use one shared listener only when actions truly share behavior; separate listener objects or Swing Action instances improve reuse and enable/disable state consistency. 100-word design defense: A payment window should own presentation only. The handler validates basic field presence, then delegates payment rules to FeeService and persistence to FeeRepository. A background worker protects the EDT from database latency. Parameterized SQL, transactions, resource closure and typed results make failures predictable. The UI displays a safe status message and exposes a receipt only after successful confirmation. Separating these responsibilities makes the service independently testable and keeps database changes from altering the window.

Unlike applet callbacks init(), start(), paint(), stop(), destroy(), a desktop Swing window is created explicitly, receives events while displayed, and is disposed by application logic. Loading doctors from a DB for each change is O(d) per query plus network latency and can show fresh data; loading once into a Map costs O(D) startup time/storage and gives expected O(1) department lookup, but can become stale and uses memory.

BorderLayout gives the results center the available extra space. The nested search and button rows use FlowLayout to preserve their preferred component sizes. GridLayout would force equal-sized cells and CardLayout is intended for swapping views, not this fixed screen. The current Task03 Swing implementation has a title/search container north, scrollable results center and footer south. Resize testing is specified at small, default and large sizes; no screenshots or actual measurements were captured.

Nested layouts are simple and resilient for grouped rows. GridBagLayout offers precise constraints but needs more setup. Absolute positioning breaks when fonts, display scaling, localization or window size change. Results should grow while search/footer rows retain preferred size.

5. Task 4 — Drawing-pad event forensics

A mouse listener fails if the wrong callback name/signature is supplied or the listener is not registered. A click label remains unchanged if the handler updates the wrong object/property. Drawing directly only inside the event handler is transient: repainting after minimize/restore clears pixels unless points are retained and redrawn. In Swing, override paintComponent, call super.paintComponent, and draw the saved model; repaint requests a later paint pass.

on mouseClicked(event):
  points.add(event.getPoint())
  label.setText("Clicks: " + points.size())
  repaint()
paintComponent(g):
  super.paintComponent(g)
  for point in points: draw dot at point

The Task04 source uses MouseAdapter, stores Point objects, updates a label and redraws in paintComponent. @Override makes a misspelled/nonmatching method fail compilation instead of silently creating an unused method. Points use O(k) memory for k clicks; repainting draws O(k) dots. A BufferedImage also preserves pixels but uses O(width × height) pixel storage and is useful for raster drawing/large histories. 6. Task 5 — Currency converter event styles

Four implementations should perform the same conversion and validation: (1) frame implements ActionListener, (2) named inner class, (3) anonymous inner class, and (4) lambda. Each registers the Convert button and amount field’s Enter action; WindowAdapter.windowClosing disposes the frame. The lambda reduces boilerplate for a single-method listener; named classes are reusable and easier to test independently; anonymous classes can access enclosing fields but are verbose; implementing on the frame can mix presentation and event roles. A method reference or shared Swing Action is appropriate when a named operation or reused command is needed.

The existing Task05 lambda source converts using illustrative fixed rates (USD 83 INR, EUR 90 INR); these are demonstration constants, not live financial rates. It rejects invalid/negative input and displays a dialog. Valid and invalid test cases are amount 10 USD→INR (expected 830.00 with the sample rate) and nonnumeric input (error dialog). These are expected behavior, not observed screenshots. Code-change counts across versions were not measured; compare by counting changed/added lines in the actual variants.

Users: students register; committee members filter and export. Screens: registration form, event list, committee registration table, filter controls, validation/confirmation dialogs. Data: event, student identity, registration and timestamp. Requirements: validate required fields, reject duplicate student/event pairs, show useful messages, preserve responsiveness, export the filtered view.

MySQL tables with foreign key and UNIQUE(student_id, event_id)

Register pseudocode: validate request; call service in SwingWorker; begin transaction; insert registration using parameterized SQL; let unique constraint reject duplicates; commit; in case of failure rollback and map unique conflict to “already registered”; update UI on EDT. Filter pseudocode: validate selected event/page; run parameterized SELECT off EDT; use LIMIT ? OFFSET ?; publish rows and page status on EDT. Export the same filtered query/result set without blocking the UI.

CREATE TABLE registrations (
  registration_id INT PRIMARY KEY AUTO_INCREMENT,
  student_name VARCHAR(100) NOT NULL,
  register_number VARCHAR(30) NOT NULL,
  event_id INT NOT NULL,
  registered_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (register_number, event_id),
  FOREIGN KEY (event_id) REFERENCES events(event_id)
);

The provided Task06 schema currently uses student_name/event_id as its uniqueness key and provides a foreign key; for a production design, register number or a stable student key is preferable to a mutable/display name. Loading 100,000 rows at once costs O(n) transfer time and O(n) client memory and can stall the EDT if done synchronously. Paginating with LIMIT/OFFSET bounds each page’s client memory to O(page size), but large offsets may still require DB work proportional to the skipped rows. Keyset pagination can improve deep-page access when allowed. Use SwingWorker for query execution and update Swing models only on EDT.
